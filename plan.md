# NFL Weekly Matchup Thesis Generator — Implementation Plan

Pulls the week's NFL schedule with win odds, aggregates news per team, and uses a
local LLM to produce a thesis on who wins each game.

**Status:** v1 complete (Stages 0–7). Stage 8 is the remaining backlog.

### Known risk, accepted

A smoke test against `qwen2.5:7b` on 2026-09-02:

> Prompt: *"Chiefs favored by 3.5 over Raiders. Who wins?"*
> Response: `{"winner": "Raiders", "confidence": 0.6}`

The model contradicted a trivial spread. The user has chosen to let the LLM make
the final pick anyway. Stage 5 therefore carries three mitigations (plain-language
probabilities, a constrained pick field, and a visible market comparison) so the
choice is transparent rather than silently wrong. See §2.

## 2. Core architecture principle

**Numbers are computed in Python. Prose is generated by the LLM.**

`probability.py` derives win probability from moneylines and removes the vig. That
number is never calculated, rounded, or restated by the model — it is passed in as
a finished fact.

The LLM's job is to read the news brief plus that probability and argue a winner.
Its pick is the report's verdict. Three guardrails keep that honest:

1. **Plain-language probabilities.** The prompt says `Seattle 62%, New England 38%`,
   never `SEA -175`. American-odds notation is precisely what the model mangled.
2. **Constrained pick field.** `pick` is a schema `enum` of the two exact team
   display names. Ollama constrains generation to the schema, so an
   out-of-vocabulary pick is *structurally impossible* rather than merely
   validated after the fact (upgraded in Stage 3; the validate-and-retry path
   remains as a backstop for semantic errors).
3. **Market shown beside the verdict.** When the LLM's pick differs from the
   de-vigged favorite, the report labels it an **upset call**. Labeling, not vetoing.

### Field-level findings (verified 2026-09-02, correcting earlier assumptions)

`competitions[0].odds[0]` on the ESPN scoreboard:

| Value | Path | Note |
|---|---|---|
| Home moneyline | `.moneyline.home.close.odds` | String, e.g. `"-175"` |
| Away moneyline | `.moneyline.away.close.odds` | String, e.g. `"145"` |
| Home spread | `.spread` (float) or `.pointSpread.home.close.line` | See sign convention below |
| Total | `.overUnder` (float) or `.total.over.close.line` (`"o44.5"`) | |
| Summary | `.details` | e.g. `"SEA -3.5"` |

**`homeTeamOdds.moneyLine` / `awayTeamOdds.moneyLine` are `null` on every game** —
those objects carry only `favorite` / `underdog` / `team`. Use the `.moneyline`
object instead. This corrected an early misread.

**Spread sign conventions are opposite between the two sources — normalise on
ingest:**

* **ESPN** `.spread` is home-relative, **negative = home favoured**.
  Verified: `NE@SEA` `details="SEA -3.5"` → `spread=-3.5` (home SEA favoured);
  `BAL@IND` `details="BAL -3.5"` → `spread=+3.5` (away BAL favoured).
* **nflverse** `spread_line` is **positive = home favoured**. Verified:
  `NE@SEA spread_line=3.5`, `CHI@CAR spread_line=-2.5` with `CHI` (away) favoured.

`models.Odds.home_spread` stores the **ESPN** convention; `sources/nflverse.py`
flips the sign on the way in.

**Cross-validation:** ESPN and nflverse agree exactly on 2026 Wk1 NE@SEA
(`-175` / `+145`, total 44.5), so nflverse is a sound fallback.

**Optional, deferred:** Open-Meteo forecast by stadium lat/lon for outdoor venues.
Free, no key. Not in v1.

### Stage 1 — Data sources and cache ✅ COMPLETE

**Goal:** every external fetch works, is parsed into dataclasses, and is cached.

- `cache.py`: SQLite at `.cache/nfl.db`, table `(key, fetched_at, payload)`.
  TTLs — odds 15 min, news 2 h, injuries 6 h, schedule 24 h. `--refresh` bypasses.
- `schedule.py`: parse the ESPN scoreboard into `Game` objects. Extract from
  `competitions[0].odds[0]`: `spread`, `overUnder`, and both teams' moneylines.
  Handle games with **no odds posted yet** — an empty `odds` array is normal early
  in the week and must not crash the run.
- `news.py`: one RSS query per team, `when:7d`, browser User-Agent. Dedupe by title
  similarity, keep the newest 40 per team, sort by date descending.
- `injuries.py`: map ESPN team IDs to teams; keep player name, status, and the
  analyst comment.
- `nflverse.py`: load `games.csv`, filter to the season/week, used only when ESPN
  has no moneyline for a game.
- Capture one real payload per source into `tests/fixtures/` so Stages 2–6 can be
  developed offline without hammering ESPN.

**Acceptance:** a script prints all 16 games for a given week with odds where
posted; a second run within the TTL makes zero network calls.

**Outcome:** all met. Live full-slate run: 16 games, 32 teams, 1280 headlines,
800 injury entries. Cold 18.7 s / 35 requests; warm 0.62 s / **0 requests**.
29 offline tests pass (`python -m unittest discover -s tests -t .`).

**Critical finding — do not set a User-Agent.** ESPN's edge returns 403 for
browser-like UAs *and* for unrecognised custom ones, but 200 for the default
`python-requests/x.y` and `curl/x.y`. Verified:

| UA sent to ESPN | Result |
|---|---|
| `Mozilla/5.0 … Chrome/124` | 403 |
| no `User-Agent` header | 403 |
| `nfl-thesis/0.1` | 403 |
| `python-requests/2.34.2` (default) | 200 |

Google News and nflverse accept the same default, so the fix is to send no
custom UA at all. Adding a "realistic" browser UA here breaks every ESPN call.
Documented in `config.py` and `sources/cache.py`.

**Validation:** ESPN and nflverse agree on **all 16** games for spread,
moneyline and total once the sign is flipped, and all 16 abbreviation pairs
align through the alias map. The fallback was force-tested by blanking every
ESPN line: 16/16 filled, and 8/8 on a partial. One benign difference —
ARI@LAC moneyline `410/-550` (ESPN) vs `425/-575` (nflverse), a genuine
book/timestamp difference, with spread and total identical.

**Also done:** `tests/fixtures/espn_injuries.json` trimmed 8.9 MB → 85 KB
(4 teams, unused `links`/`headshot` blobs stripped); `nflverse_2026_wk1.csv`
fixture added. `nflverse.fill_missing` split into a network half and a pure

### Stage 2 — Probability engine ✅ COMPLETE

**Goal:** trustworthy win probabilities, fully deterministic and tested.

American moneyline to implied probability:

```
ml < 0:  p = (-ml) / (-ml + 100)
ml > 0:  p = 100 / (ml + 100)
```

Remove the vig by normalizing the pair:

```
p_home_devig = p_home / (p_home + p_away)
```

- Fall back to a spread-to-probability conversion when moneylines are missing
  (logistic on the spread, calibrated against nflverse historical results).
- Expose the raw pair's overround so the report can note how much juice was baked in.

**Acceptance:** `tests/test_probability.py` passes on hand-checked cases —
a pick'em (`-110/-110` → 50/50), a heavy favorite, a heavy underdog, and a
missing-moneyline fallback. Probabilities always sum to 1.0 within float tolerance.

**Outcome:** all met. 58 tests pass across the suite. All 16 Wk1 games produce
probabilities whose favourite agrees with the spread sign; median book vig 4.3%.

**Spread fallback is fitted, not guessed.** `SPREAD_LOGIT_PER_POINT = 0.13932`,
derived by least squares through the origin on logit(de-vigged market
probability) vs `spread_line` over the 5,407 nflverse games carrying both a
spread and both moneylines.

* Through-origin is justified empirically: the free-intercept fit returns
  intercept `0.0063` — a pick'em is a coin flip.
* Fit vs market probability: mean abs err `0.0147`, median `0.0128`, p95 `0.0348`.
* **Validated against real outcomes** on 6,952 regular-season games (ties
  dropped): n-weighted mean abs calibration error `0.0243`, Brier `0.2118`
  against `0.2500` for a coin flip.
* On the live Wk1 slate the fallback lands within **1.68pp mean / 3.47pp max**
  of the moneyline path.

Reproduce with `python -m tests.calibrate_spread` (`tests/calibrate_spread.py`)
if the historical data is refreshed.

**Guardrail landed early:** `probability.plain_language()` renders the model's
view of a line as `"Seattle Seahawks 61%, New England Patriots 39%"`, and a test
asserts the string contains no American odds. This is guardrail #1 from §2,
enforced at the source rather than in the Stage 5 prompt.

Note: the hand-checked literals in the first draft of the tests were rounded
wrong in the 4th decimal (0.6196 vs the true 0.61954). The code was correct; the
constants were fixed.

### Stage 3 — LLM client ✅ COMPLETE

**Goal:** a reliable JSON-in/JSON-out call against `qwen2.5:7b`.

- POST to `/api/chat` with `stream=false`, `format=json`,
  `options={"num_ctx": 16384, "temperature": 0.2}`.
- Validate the response against the expected keys for the calling stage.
- Retry up to 2× on malformed JSON, missing keys, or an out-of-vocabulary `pick`.
- Log token counts (`prompt_eval_count`, `eval_count`) and wall time per call so
  the full-week runtime is measurable.
- Timeout generously — a cold model load took ~8 s in testing.

**Acceptance:** a canned prompt round-trips to a validated dataclass; a
deliberately malformed-response test exercises the retry path.

**Outcome:** all met. 80 tests pass (22 new, fully mocked — no host needed).
Live-verified: health check, enum-constrained pick, and a forced validator
rejection that retried and obeyed the correction.

**Upgrade — schema-constrained generation.** Ollama 0.20 accepts a full JSON
schema as `format`, not just `"json"`. Generation is constrained to match, so
`enum` fields cannot come back out-of-vocabulary. This strengthens guardrail #2
from a post-hoc check to a decoding constraint. `minItems` / `maxItems` /
`maxLength` are all honoured, which Stage 4 uses to bound output.

**Performance — measured, and it revises the estimate.** The host is
generation-bound at **~10 tok/s**. Everything else is noise:

| Lever | Result |
|---|---|
| `num_ctx` 2048 / 4096 / 16384 | 9.9 / 10.1 / 9.0 tok/s — no effect. Keep 16384 for headroom. |
| 2 concurrent workers | 1.10x — negligible |
| 4 concurrent workers | **0.83x — actively worse**; the host serialises |
| Bounded schema + terse prompt | 20.2s → 5.5s (3.7x), but over-complied (2 storylines) |
| `minItems:3, maxItems:4` | ~10s/brief holding 4 storylines — the chosen balance |

So the only real runtime control is **generated tokens**, via schema bounds and
`num_predict` (added to `config` as `OLLAMA_NUM_PREDICT = 400`). Parallelism is
off the table.

**Revised runtime estimate:** ~10s per team brief and ~15s per game thesis gives
roughly **9–11 minutes** for a cold full week, against the 5–10 minutes guessed
in §5 Stage 7. Cached reruns stay near-instant for the data layer.

**Also confirmed:** with plain-language probabilities the model picked the
favourite correctly, where the §1 raw-odds smoke test picked wrong. Direct
evidence that guardrail #1 does real work.

### Stage 4 — Stage-1 LLM pass: team briefs ✅ COMPLETE

**Goal:** compress ~40 headlines + injuries per team into a ~200-token structured brief.

32 calls per week, one per team. This map step exists because 32 teams × 40
headlines cannot fit in a 7B model's usable context in a single call.

Input: team name, headlines (title + source + date), injury rows.
Output JSON: `{injuries: [], storylines: [], momentum: str, sentiment: str}`.

Prompt must instruct: summarize only what the headlines say, do not speculate about
the outcome of any game, do not invent player names.

**Acceptance:** all 32 briefs generate and validate; spot-check three against the
raw headlines for fabricated content.

**Outcome:** all met. 32/32 briefs, **0 failures, 0 retries**, 689.9 s cold.
96 tests pass (16 new, mocked). Spot-checks are clean.

**The first 32-team run failed on quality, and live data was the only way to see
it.** Three problems, all invisible in the single-team Stage 3 test:

| Problem | Evidence | Fix |
|---|---|---|
| Storylines were restated injuries, ignoring all 40 headlines | ~100% injury-flavoured; KC/SEA/BUF each returned 3 injury lines | Headlines moved **before** injuries in the prompt, with an explicit "do not summarise injuries back" rule |
| `sentiment` carried no signal | `mixed` for **28 of 32** teams | Field dropped |
| `injuries` was ESPN data laundered through the model | Wasted generation, fabrication risk, crowded out news | Injuries now bypass the LLM entirely and pass through from ESPN |

The third fix is the project principle applied one level deeper: the model
produces prose, structured facts come from the source. Results after the change:

| Metric | Before | After |
|---|---|---|
| Injury-flavoured storylines | ~100% | **5%** |
| Grounding (storyline words found in that team's headlines) | 0.58 | **0.70** |
| Generated tokens, 32 teams | 4,735 | **2,451** |
| Seconds per brief | 26.0 | **15.4** |

**Response caching added.** LLM replies are content-addressed in the same SQLite
cache — the key hashes model, schema, system and prompt, so a changed headline
or edited template invalidates naturally and the TTL is only a backstop. A warm
rerun of all 32 briefs takes **0.7 s / 0 LLM calls**, which is what made the
before/after comparison above affordable.

**Runtime correction.** Stage 3 estimated ~10 s per brief from a benchmark that
re-sent an *identical* prompt, so llama.cpp reused the cached KV prefix and
prompt evaluation was nearly free. Real briefs each carry a distinct ~1,400-token
prompt and pay full prompt eval. True cost is **15.4 s per brief** (~8 min for
32), against the 10 s assumed. Stage 5's estimate should be treated the same way
until measured.

**Layout note:** Stage-1 logic lives in `nfl_football/briefs.py` rather than
inside `pipeline.py` as §4 sketched, keeping prompt, schema and parsing for each
LLM stage in its own module. Stage 5 will mirror this with `theses.py`.

### Stage 5 — Stage-2 LLM pass: game theses ✅ COMPLETE

**Goal:** the verdict. Two calls per game, 32 per week.

Input: both team briefs, kickoff time, spread, over/under, and the de-vigged
probabilities **as plain-language percentages**.

Output JSON:

```json
{
  "pick": "<exact team display name>",
  "confidence": "low|medium|high",
  "thesis": "<2-4 sentence argument>",
  "key_factors": ["...", "...", "..."],
  "news_vs_market": "<how the news lines up with the odds>"
}
```

Apply all three guardrails from §2. Compute `is_upset_call` in Python by comparing
`pick` against the de-vigged favorite — never ask the model to self-report it.

**Acceptance:** all 16 games produce a valid pick matching one of the two team
names; upset calls are correctly flagged; no thesis restates a probability that
differs from the computed one.

**Outcome:** all met. 16/16 valid picks, **0 failures, 0 retries**, 507 s for 32
calls. 128 tests pass (25 new).

**The single-call design failed the user's intent, and live data showed it.**
First full run: the model picked the market favourite in **16 of 16** games and
reported `"high"` confidence in **16 of 16**. A controlled experiment — same
prompt with the market section removed — flipped **3 of 8** picks, proving the
news carried an independent signal that the visible probability was suppressing.
With the pick always equal to the favourite, the entire ~11-minute news pipeline
contributed nothing to the verdict.

**Resolution (user decision):** two calls per game.

1. **Blind pass.** `prompts/news_lean.txt` contains no betting information of any
   kind — no spread, total, probability or the word "market". A test asserts that
   isolation, since one leaked token would undo the whole mechanism. Returns
   `news_lean` (enum of the two teams) + `lean_reason`.
2. **Verdict pass.** Sees the market *and* its own blind read, then picks.

`confidence` is no longer asked of the model — it is derived in Python from the
de-vigged margin (`probability.confidence_label`): ≥70% high, ≥55% medium, else
low. Same reasoning that retired Stage 4's `sentiment`.

| Metric | Single-call | Two-call |
|---|---|---|
| Upset calls | 0/16 | **5/16** |
| Confidence values | `high` ×16 | 10 medium / 3 high / 3 low |
| Calls per week | 16 | 32 (+2.6 min) |

**Caveat, stated plainly:** the final pick matched the blind news lean in **all
16** games — the verdict pass never overrode its own lean. So the market now
carries no weight in the pick, the mirror image of the original failure. In
practice this behaves close to the "news-only pick" option, with the market shown
for contrast rather than genuinely weighed. The `do not default to the market`
instruction likely over-corrected. Whether that is right is an empirical
question, and **Stage 8's picks-vs-results log is the only way to settle it**:
market favourites win ~66% of the time, so disagreeing on 31% of games is a real
bet on the news signal.

`Thesis` now carries `news_lean`, `lean_reason` and a `lean_differs_from_pick`
property so the report can show news lean, market favourite and final pick side
by side.

### Stage 6 — Rendering ✅ COMPLETE

**Goal:** both output formats.

Per game, both renderers show: matchup and kickoff, spread and total, de-vigged
win % per side, **the LLM's pick** as the verdict, the market favorite beside it,
an upset-call badge when they differ, the thesis, key factors, injury callouts,
and linked source headlines.

- `markdown.py` — stdout, terminal-width aware.
- `html.py` — Jinja2 into a single self-contained file, CSS inlined, no external
  assets. Week overview at the top, per-game cards below.

**Acceptance:** a full week renders in both formats; every headline referenced in a
thesis is traceable to a link in the sources list.

**Outcome:** all met. Full week renders to both formats — 16 games, 7 upset
calls, **320 source links**, 216 KB self-contained HTML. 151 tests pass (23 new).
Both renderers show news lean, market favourite and final pick side by side.

**Two bugs found by looking at the rendered page, not by testing markup:**

1. **Every probability bar rendered empty.** `.track` and `.fill` were `<span>`s
   without `display: block`, so they computed to `display: inline` with
   width **0px** and height **0px**. The markup test asserting `width: 60.9%`
   passed the whole time — the string was present, it just did nothing. Verified
   in-browser before and after: fill/track ratio is now `0.609`, matching the
   probability exactly. Added a regression test that inspects the CSS rules
   rather than the inline style.
2. **Key factors were cut off mid-word** ("suggesting a cohesive and re-").
   `maxLength` in the schema is a hard grammar constraint — the decoder closes
   the string at the limit regardless of where the sentence is. Raised to 170
   with explicit "at most 15 words" guidance in the prompt, giving headroom
   rather than a hard stop. Re-measured: **0** factors now hit the limit.

**Operational note — the LLM cache invalidates when the line moves.** Because
keys hash the full prompt and the prompt carries the spread, total and provider
line, any odds movement re-runs the thesis calls. Correct behaviour (a stale
thesis about a moved line would be wrong), but it means reruns are only free
inside ESPN's 15-minute odds TTL. Observed: a rerun after both news and odds
refreshed cost the full 992 s; a rerun touching only the thesis template cost
209 s with 48 of 64 calls served from cache.

**Layout note:** `pipeline.py` was written here rather than in Stage 7, since the
renderers need assembled `GameReport` objects. Stage 7 adds only the CLI on top.

### Stage 7 — CLI, email and end-to-end ✅ COMPLETE

**Goal:** one command runs the whole thing.

```bash
python -m nfl_football --week 1 --season 2026 --html report.html
```

Flags: `--week`, `--season`, `--game KC@LV` (single game), `--refresh` (bypass
cache), `--no-llm` (odds and news only, useful for debugging sources),
`--no-html`, `--quiet`, `--no-sources`.

**Display timezone (added at user request).** Kickoffs arrive from ESPN in UTC
and are converted to `America/Toronto` for every reader-facing surface — both
renderers, the email body, and the LLM prompt. `config.to_local()` uses stdlib
`zoneinfo`, so no new dependency; `NFL_TZ` overrides the zone.

This changes the **day**, not just the clock, which is why UTC was actively
misleading: the Monday night game displayed as "Tue 00:15Z" and the opener as
"Thu 00:20Z" when it kicks off Wednesday evening locally. The Sunday slate now
reads as the familiar 13:00 / 16:25 rather than 17:00 / 20:25.

The prompt was converted too, at the cost of invalidating the cached theses
(5m37s to regenerate): UTC had been telling the model the wrong day of week,
which bears on rest days and short weeks. Tests cover the day-rollback case,
EDT/EST either side of the DST change, and naive-datetime handling.

**Email body is a separate template — mail clients are not browsers.** The
standalone report is built on CSS custom properties, flexbox/grid and
`<details>`; Gmail strips `var(--x)` and (on mobile, non-Gmail accounts) whole
`<style>` blocks, Outlook's Word engine has no flexbox or grid, and no client
supports `<details>`. `render/template_email.html.j2` is therefore table-based
with every style inlined and a fixed light palette, verified by tests that assert
none of those constructs appear.

**Size.** Gmail clips bodies over ~102 KB behind "View entire message". The full
report is 217 KB, so it cannot be the body. The email template omits source links
(they live in the attachment) and **degrades automatically**: the full body is
rendered, and if it would clip it is re-rendered without per-game injuries and
"news vs market". Measured for a 16-game week: 82 KB as sent, 95 KB worst case at
maximum content length — both under the limit, so compact never triggers for a
real week. `mailer.clipping_warning()` reports it either way.

**Attachment.** The full standalone `report.html` (217 KB, dark mode, all 320
source links) rides along as an attachment, so nothing is lost from the body trim.

A layout bug surfaced while size-testing: a long unbroken token — synthetic
`"x"*520`, but a bare URL in a headline would do it — widened the table to

**Email (added at user request).** `--email` sends the HTML report;
`--email-to ADDR` overrides the recipient (default `kevin.wood75@gmail.com`);
`--email-dry-run [PATH]` writes the exact message to a `.eml` for inspection and
sends nothing. Messages are `multipart/alternative` — markdown as the text part,
the full styled report as HTML.

**Credential handling:** SMTP settings (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASSWORD`, `SMTP_FROM`) come from a **`.env` file** in the project root,
loaded by `python-dotenv` at the top of `config.py` — before anything reads the
environment. `.env` is gitignored; `.env.example` ships placeholders only.

* **Precedence:** `override=False`, so an exported variable beats the file. A
  one-off run can use different settings without editing `.env`.
* `NFL_ENV_FILE` points at an alternative file.
* **Permissions:** `config.env_file_warning()` warns when `.env` is group- or
  world-readable and tells the user to `chmod 600`. Surfaced by `--check-email`
  and before any send.
* **`--check-email`** reports what is configured and exits without running the
  pipeline. It prints the host, user and recipient but the password only as
  `***set***`.
* `SmtpConfig.__repr__` redacts the password; tests assert the secret never
  appears in the repr or in `--check-email` output.
* Gmail needs an **App Password**; the auth-failure path says so explicitly
  rather than reporting a bare `535`.
* Nothing is ever sent without an explicit `--email`.
